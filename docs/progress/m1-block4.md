# M1 第四块：知识库（进度与拆分）

依据 PRD 的 FR-16、FR-17、FR-18、§9.4、AC-04，以及 decisions.md 的 D-14（文件级权限 RAG）、D-21（资源 ACL 与部门继承）、D-24（RAG 全部用 Go，向量存 pgvector）、D-27（ACL 检索分档与性能基线）、D-33（部门管理员默认共享范围）。本块只做 P0；FR-19（Rerank、检索测试台）是 P1，不在本块。

## 范围与技术要点

- **解析**：复用第三块 `internal/docparse`（txt / md / docx / xlsx / pptx / 文本 PDF）。版本按 `hengdesk-spikes/pdf-docx/REPORT.md` 锁定。REPORT 第 7 节为 Go 1.25 选了 go-pdfium v1.19.8 和 excelize 伪版本；D-29 已把工具链改为 Go 1.26，所以沿用 REPORT 第 3 节实测过的 Go 1.26 版本：**go-pdfium v1.21.4**（每页约 1.5–3 ms）和 **ledongthuc/pdf 20261020125853**，并由 govulncheck 门禁兜底。扫描件给出明确提示「不支持 OCR（规划中）」。
- **异步管线**：上传 → 对象存储 → asynq 任务 `kb:index`（worker 进程执行）：解析 → 切分 → 经网关调用 embedding → 写入 `kb_chunks`。状态为 `pending / parsing / indexing / ready / failed`；失败时记录原因，可以重试。
- **存储**：`kb_chunks` 为手写迁移（不进 ent），字段有 `file_id`、`kb_id`、`embedding vector(1024)`、`tsv tsvector`。HNSW 索引（`vector_cosine_ops`，m=16，ef_construction=64），`file_id` 用 B-tree 索引，`tsv` 用 GIN 索引。中文全文检索在 Go 里用 gse 分词，再以 `simple` 配置写入 tsvector。
- **ACL（D-14 / D-21）**：复用现有 `acl` 表。资源类型为 `kb` 和 `kb_file`。文件未单独设置权限时继承知识库权限。检索时先算出 `allowed_file_ids`，再在同一条 SQL 中用 `file_id = ANY($1)` 预过滤。修改 ACL 只改元数据，不重建索引。
- **分档检索（D-27）**：按可见 chunk 数选择策略。小候选集走精确检索（B-tree 预过滤加距离排序）；大候选集走 HNSW，配合 `SET LOCAL hnsw.iterative_scan = relaxed_order` 和 `ef_search`，外层再按距离重排。HNSW 返回不足 k 条、但可见总数不少于 k 时，回退到精确检索，**不允许静默低召回**。向量和全文两路结果用 RRF 融合。
- **引用**：对话绑定知识库后，每次提问先检索。命中的片段编号后放进上下文，并通过第三块预留的 `citation` SSE 事件下发，同时写入消息的 `citations` 字段（含文件名、file_id 和片段位置）。用户没有任何可见文件时，返回「没有可用资料」，不调用检索结果。
- **CI**：embedding 只用 mock（mockupstream 新增 `/embeddings`，确定性的词袋哈希向量），不读取任何真实密钥。召回回归测试在 PostgreSQL 17 + pgvector 任务中跑，覆盖可见比例约 1% 和约 50% 两档。
- **性能复测**：100 万 × 1024 维只在本地跑，不进 CI。结果写入本文档，另给产品经理一份摘要，用于定稿 D-27。

## 待确认（先按以下默认值实现，不阻塞开发）

1. **向量维度固定为 1024**：`kb_chunks.embedding` 列为 `vector(1024)`（HNSW 需要固定维度）。embedding 模型返回的维度不是 1024 时，文件标记为失败，原因写明维度不符。bge-m3、Qwen text-embedding-v3/v4（1024）都满足。以后要支持其他维度，需要新增列和索引。
2. **embedding 模型的选择**：每个知识库在设置里选一个平台模型（模型管理里登记的模型名），建库时必填。更换模型触发全库重建；重建期间旧索引继续可用（PRD 边界条件）。本块先实现「保存新模型 + 全部文件重新入队」，旧 chunk 在新 chunk 写入后按文件替换。
3. **切分默认值**：chunk 大小 800 字符，重叠 100 字符，可在知识库设置里改（范围 200–4000，重叠小于大小的一半）。M0 没有调参数据，等有真实文档后再调。
4. **检索默认值**：top-k = 8 条进入上下文；向量路和全文路各取 40 条做 RRF（k=60）。分档阈值：可见 chunk 数 ≤ 20,000 时走精确检索，否则走 HNSW（ef_search=100）。阈值依据 M0 的 30 万数据，100 万复测后再定。
5. **权限位含义**：员工能检索某文件，需要对该文件（自定义权限时）或其知识库（继承时）有 `view` 位。上传 / 删除文件、重试需要知识库的 `edit` 位；改设置、改权限、删除知识库需要 `manage` 位。超级管理员不自动获得任何知识库的内容权限（与 D-21「三员分立」一致），需要被显式授权。
6. **文件去重**：同一知识库内上传内容哈希相同的文件，不重复入库，返回已有文件并提示「内容相同的文件已存在」。文件名相同但内容不同时，自动改名为「名称 (2).ext」后入库并提示。
7. **单文件大小上限**：默认 50 MB（环境变量 `HENGDESK_KB_FILE_MAX_MB`），比会话文件的 20 MB 宽。
8. **对话如何绑定知识库**：智能体（FR-20）在第五块才做。本块先让用户在对话里勾选自己可见的知识库（每个会话最多 5 个），保存在会话上。第五块改由智能体绑定。
9. **检索日志**：每次检索写一条审计 `kb.retrieve`，记录 kb_ids、可见文件数、命中 file_id 与 chunk 位置、所用策略和耗时，不记问题原文和片段内容。AC-04 以此日志验证。
10. **删除知识库**：软删除知识库记录，同步删除其全部文件、chunk 和原件。
11. **文件自定义权限的可见范围**：文件切换为「自定义」后，只有被单独授予该文件 `view` 的人，以及知识库 `manage` 持有者可见；知识库的 view / edit 持有者不再自动可见。文件级授权只有 `view` 一档。
12. **embedding 不受预算拦截**：索引是后台任务，不按 FR-31 预算拦截；用量照常记到上传者名下（purpose=embedding），在用量统计里可见。是否要按部门预算拦截索引，请确认。
13. **embedding 模型不做模型使用权限检查**：知识库设置里选的模型只要存在且启用即可。模型级使用 ACL 在后续块统一处理。
14. **不能撤销最后一个 manage**：撤销或降级知识库最后一个 `manage` 授权返回 409，避免知识库无人可管。
15. **任务补偿**：`kb:sweep` 每 5 分钟把 pending 超过 2 分钟的文件重新投递，把 parsing / indexing 超过 40 分钟（超过任务超时 30 分钟）的退回 pending 再投递，防止 Valkey 丢任务或 worker 崩溃后文件卡住。
