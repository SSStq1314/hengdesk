# D-27 复测摘要（给产品经理定稿用）

复测日期：2026-11-04（本地，不进 CI）。工具：`server/cmd/kbbench`。原始日志与 JSON：`docs/progress/d27-retest-data/`。

## 结论（一句话）

**在本次 16 GB 内存的 8 核测试机上，100 万 × 1024 维未达标。** 可见约 1%（精确档）基本达标，召回 1.0，但向量段 P95 为 54–56 ms，略高于 50 ms；可见约 50%（HNSW 档）向量段 P95 为 427–2398 ms，比 50 ms 高一到两个数量级；在默认 ef_search=100 时召回只有 0.75–0.78，低于 0.95。全部查询都没有越权命中。主要瓶颈是内存：HNSW 索引 7.8 GB，加上表数据共 13 GB，在 16 GB 内存的机器上缓存不下。

## 环境与数据

| 项 | 值 |
|---|---|
| CPU / 内存 | Intel Xeon（虚拟机）8 vCPU / 16 GB，无 swap |
| 数据库 | PostgreSQL 17.11 + pgvector 0.8.7，shared_buffers 2 GB，maintenance_work_mem 4 GB（建索引时） |
| 数据 | 100 万切片 × 1024 维，10 万文件（每文件 10 片），100 个知识库；向量为 256 个簇中心加噪声（noise=0.03，与簇中心余弦约 0.7，接近真实 embedding 的聚类程度） |
| 索引 | HNSW m=16、ef_construction=64，索引 7.8 GB，表连同全部索引 13 GB |
| 灌数据 / 建索引 | COPY 3 分 13 秒；HNSW 加 ANALYZE 10 分 56 秒 |
| 检索参数 | top-k 8，每路 40 条，RRF k=60，精确档阈值 20,000 可见切片 |
| 口径 | 端到端 = `Retriever.Retrieve` 全链路（ACL 计算 → 可见文件 → 向量路 + 全文路 → RRF → 写审计），**不含**问题 embedding 的网络耗时（本地用确定性函数代替）；向量段 = 带 ACL 预过滤的向量 SQL；recall = 向量路 recall@40，与同一可见范围内的精确 top-40 比较 |

|---|---|---|---|---|---|---|
| 冷缓存，ef=100（200 次） | 1% | 精确 | 48 / 73 | 44 / 69 | 1.000 | 0 |
| 冷缓存，ef=100 | 50% | HNSW | 501 / **2644** | 394 / **2398** | **0.748** | 0 |
| 热缓存，ef=100（100 次） | 1% | 精确 | 52 / 71 | 43 / **54** | 1.000 | 0 |
| 热缓存，ef=100 | 50% | HNSW | 319 / **568** | 210 / **471** | **0.778** | 0 |
| 热缓存，ef=400 | 1% | 精确 | 50 / 89 | 45 / **56** | 1.000 | 0 |
| 热缓存，ef=400 | 50% | HNSW | 266 / **532** | 166 / **427** | **0.936** | 0 |

补充档（参考）：10% 可见时，ef=100 的向量段 P95 为 2569–3579 ms，recall 为 0.93–0.96；ef=400 时 P95 为 482 ms，recall 为 0.966。100% 可见时，ef=100 的向量段 P95 为 224 ms，recall 为 0.746；ef=400 时 P95 为 303 ms，recall 为 0.894。

另做了一次纯随机向量（noise=0.35）的对照：HNSW 档 recall 只有 0.01–0.04，这是高维随机数据本身的特性，不代表真实情况，所以不作为结论依据（见 `bench-noise035.log`）。

## 复测中发现并已修复

- 可见文件超过 65,535 个时，`kbfile.IDIn(...)` 会超出 PostgreSQL 扩展协议的参数上限，检索直接报错（100% 档触发）。现在改为每批 20,000 个分批读取（`kb.loadFiles`），并补了集成测试 `TestPGLoadFilesManyIDs`。

## 优化建议（按投入产出排序）

1. **把 ef_search 默认值调到 400**：在 50% 档上，召回从 0.78 提到 0.94，P95 反而从 471 ms 降到 427 ms（iterative scan 的轮数变少了）；在 10% 档上，P95 从 2.6 s 降到 0.48 s。代价是 100% 档的 P95 增加约 80 ms。（待确认第 25 条）
2. **用 halfvec 存储或建索引**：`(embedding::halfvec(1024))` 加 `halfvec_cosine_ops` 可以把索引减到约 4 GB，让热数据进内存，召回损失通常不到 0.01。需要一次迁移并重建索引，单独开 PR 实测。
3. **硬件下限**：按「HNSW 索引加表数据 ≤ 可用内存的 70%」估算，100 万 × 1024 维 float32 至少需要 32 GB 内存（如果用 halfvec，24 GB 也许够）；shared_buffers 设为内存的 25–40%；部署后用 pg_prewarm 预热索引。（待确认第 26 条）
4. **大可见集不再传文件 id 数组**：可见比例高时，把 `file_id = ANY(10 万个 id)` 换成按知识库过滤（`kb_id = ANY(...)`），再减去「自定义权限且不可见」的少量文件。这样可省掉 50–100 ms 的元数据加载和数组传输（50%/100% 档端到端与向量段之间约有 100–200 ms 的差）。
5. **按租户或知识库分区**：数据量继续增长时，按 org 或 kb 做 list 分区，并给每个分区单独建 HNSW 索引，让精确档覆盖更多场景。
6. **1% 精确档的余量**：P95 54–56 ms，略高于 50 ms。可以把阈值从 20,000 降到 10,000，或加 `(file_id) INCLUDE` 之类的覆盖手段；也可以接受 60 ms 作为精确档的目标。

## 需要产品经理拍板

- D-27 的目标值是否改为分硬件档，例如「32 GB 及以上内存：向量段 P95 ≤ 50 ms；16 GB：不承诺」，或者按可见比例分别给出目标。
- recall 目标 ≥ 0.95，是否要求在 50% 可见、热缓存的条件下达到（需要 ef ≥ 400，加 halfvec 或更大内存）。

## D-42 复测（2026-11-04，ef_search=400 + halfvec 索引，本机 16 GB）

> **32 GB 机器上的复测待做，是 M1 验收的前置条件。** 本次只是在现有测试机上按 D-42 改完后复测一次，硬件低于推荐档，结果仅供参考。

环境：同上一轮（8 核 / 约 16 GB 内存，PG 17.11 + pgvector 0.8.7，shared_buffers=2GB，`kbbench` 库 100 万条 × 1024 维，noise=0.03，100 个知识库，每档 200 次查询、30 次抽样算召回）。
重建 halfvec HNSW 索引用时 2 分 26 秒；索引 **2.6 GB**（float32 索引理论上约为其两倍），`kb_chunks` 表加索引共 8.1 GB；`kbbench` 先用 pg_prewarm 预热（2 秒），即热缓存。recall 真值为同一可见集合上的 float32 精确结果。

命令：`go run ./cmd/kbbench -db ... -reindex -mwm 3GB`（ef=400），以及 `-ef 1000` 对照。

|---|---|---|---|---|---|---|---|

| 400 | 10% | HNSW | 38 / 55 | 17 / 29 | 0.920 | 0.903 | 0 |
| 400 | 50% | HNSW | 126 / **169** | 30 / **57** | **0.890** | 0.889 | 0 |

对照 D-42 目标（本机低于推荐硬件，仅参考）：

| 目标 | 结果（ef=400） |
|---|---|
| 精确档向量段 P95 ≤ 100 ms | 51 ms，**达标** |
| HNSW 档 50% 可见 + 热缓存 recall@10 ≥ 0.95 | 0.890，**未达标**（ef=1000 时 0.953 达标） |
| HNSW 档向量段 P95 ≤ 200 ms | 50% 档 57 ms、100% 档 71 ms，**达标** |
| 端到端 P95 ≤ 500 ms | 最高 288 ms（100% 档），**达标** |
| 越权命中 0 | 全部档位 0，**达标** |

观察：

- halfvec 让索引能整体进缓存，延迟大幅下降：50% 档向量段 P95 从 427 ms（float32 + ef=400）降到 57 ms。
- 召回有损失：同为 ef=400，50% 档 recall 从 0.936（float32 索引）降到 0.890，比预期（< 0.01）大，推测是半精度候选阶段的排序误差在聚类很紧的数据上影响较大；外层已按 float32 重排，但候选集本身有偏差（未进一步验证）。
- 把 ef_search 提到 1000 后 50% 档 recall@10 0.953、向量段 P95 51 ms，延迟仍有很大余量。**建议**：32 GB 复测时同时测 ef=400 / 1000；若 ef=400 仍不达标，把默认值改为 1000（需产品经理确认，本 PR 按 D-42 保持 400）。
- 100% 档 ef=1000 时 recall 0.933，D-42 未对 100% 档设召回门槛，记录备查。
- 原始输出：本机 `/workspace/d42stash/bench1.log`、`bench_ef1000.log`（未入库）。
