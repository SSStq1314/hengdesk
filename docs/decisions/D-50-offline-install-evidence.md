# D-50 M1 干净断网安装的证据口径

> 同步自产品决策 `decisions.md`（2026-11-11 PT，补充 D-46 第 8 条）。下面是原文。工程上怎么取证见后文，不改写决策。

- 全新 GitHub 托管 x86 VM 可以作为 M1 干净断网安装的实测环境；只证明该云 VM 环境通过，不等同于物理机、客户现场或其他架构通过。本条确认验收方法，不代表测试已经通过。
- 准备阶段允许预装文档列明的宿主依赖（如 Docker / Compose），并传入待验收的正式离线包。产品及其数据库、缓存、对象存储等运行镜像必须在隔离之后由正式包加载；不得依赖准备阶段预拉的产品镜像或既有容器、数据卷、数据库及模型缓存。安装前保留清洁基线清单。
- 隔离后禁止出站、拉取及构建；覆盖宿主、容器转发链和 IPv6，不得借宿主代理、DNS 或其他转发路径绕过。若 CI 必须保留控制通道，需明确记录范围，并确保安装进程及产品容器不能借其访问外网；否则只能称为受限出站测试，不能称为本项断网安装通过。
- 证据包含源码提交及正式包版本、包 SHA256、宿主与依赖版本、清洁基线、完整安装和验收日志、隔离规则与计数器、宿主及容器 IPv4/IPv6/DNS 出站失败探针、隔离后出站记录。失败探针必须实际发起连接；仅 DNS 失败不足以证明 IP 直连受阻。探针流量和产品自身的外连尝试应区分记录。
- 安装必须使用无 mock 的默认正式包，在全新数据库完成初始化、服务健康检查及离线验收脚本；重启后健康和数据持久性检查通过。离线安装验收不要求云模型可用，通义契约回放与 vLLM CPU 真模型冒烟单独提供证据，不得将回放宣称为通义真实服务通过。
- 满足上述条件即可作为 D-46 所需证据，不增加 M1 物理机或客户现场验收门槛；任何步骤因资源不足未完成均记为未验证，不得标为通过。

## 本仓库的取证边界

工作流：`.github/workflows/d50-offline-install.yml`。脚本：`tests/acceptance/ci/d50-offline-install.sh` 与 `tests/acceptance/offline-formal-accept.sh`。

- **准备阶段（有网）**：GitHub 托管 `ubuntu-24.04` 上已有的 Docker / Compose，加上 `pack-offline.sh` 打出的**默认正式包**（无 `--with-acceptance`，包内无 `hengdesk/mocks`）。
- **清洁基线**：删掉容器、卷、镜像、构建缓存和 Hugging Face 缓存，并在启用 IPv6 后再次清空。基线清单里不得再有产品或依赖镜像。产品镜像只在隔离之后 `docker load` 包内 tar。
- **受测边界**：安装进程在网络命名空间 `hd-sut`。该命名空间的 IPv4/IPv6 默认路由指向 veth，宿主转发链对这条 veth 全部拒绝。容器公网 IPv4/IPv6 走 `DOCKER-USER` 拒绝。dockerd 所在 uid 的新公网连接拒绝。除 runner uid 以外，发往公网解析器的 53 端口拒绝，避免 daemon 或 resolved 代解析。
- **控制通道（保留，且安装进程与产品用不上）**：init 网络命名空间里 **runner uid** 到 GitHub 的 443 和该 uid 的 DNS。用来维持 Actions 心跳，并在拆除隔离后上传 artifact。证据里记录一条当时的公网 443 对端地址；`hd-sut` 和容器对该地址以及 `1.1.1.1` / `8.8.8.8` / `2606:4700:4700::1111` 的 TCP 必须失败，DNS 查询也必须失败。探针计数在安装、验收窗口之外单独增加；这两个窗口内拒绝计数不得增加。
- **验收**：新库 healthz、未登录 401、登录、写入部门标记、重启后标记仍在，并查询 `users` 行数。不要求云模型。含 mocks 的 15 步 CI 不是本项。
- **结论范围**：只覆盖这一台云上 x86 VM。不写成物理机或客户现场通过。job 失败或资源不足就是未验证。

隔离在上传 artifact 之前拆除，避免把 runner 自己的结果回传链路一起封死。
