# Spike 2：pgvector HNSW + KB ACL 预过滤（D-12）

日期：2026-11-02（America/Los_Angeles）　状态：**已实测，但规模是缩小后的**

## 0. 测试环境与规模（注意与 PRD 的差距）

- PostgreSQL 17 + pgvector 0.8.7，跑在本机 box 上（8 vCPU、15 GB 内存），数据目录 /workspace/pgdata，监听 55432 端口。
- 数据规模：**30 万 chunk × 768 维**（cosine）。PRD 目标是 100 万 × 1024，受内存限制缩小。**100 万/1024 维的结果没有实测**，需要在目标硬件上用同一程序重跑（`-n 1000000 -dim 1024`）。
- 向量是合成数据：200 个聚类中心加噪声，查询点从聚类附近随机取，不是真实 embedding 分布。召回率的绝对值只能作参考，**不同方案之间的相对差异才是结论**。
- ACL 模型：每个 chunk 带 `acl int[]`（principal 列表），查询条件 `acl && $principals`，用 GIN 索引支持。可见比例分 1% / 10% / 50% 三档。
- 共 50 个 KB；额外建了一张按 `kb_id` 做 LIST 分区的表 `chunks_kb`，每个分区有自己的 HNSW 和 GIN 索引。
- HNSW 参数 m=16、ef_construction=64；top-k=10；每个配置跑 200 条查询；召回率以精确检索结果为基准。
- 建库耗时：COPY 写入 8.9 s；单表 HNSW 建索引 31.4 s；分区表 HNSW 2 min 29 s。
- 原始数据：`results-300k.json`、`bench-300k.log`（每个配置都带 EXPLAIN 计划）。复现：`./pgbench-acl -cmd load|index|bench`。

## 1. ⚠️ 测试方法上的坑（第一次结果作废）

第一次运行时，HNSW 的耗时和精确检索一样，而且在 iterative_scan=off 时召回率也是 1.0，结果不可信。原因是 **pgx 默认缓存 prepared statement，PG 复用了在 `enable_indexscan=off` 下生成的 generic plan**，所以改了 GUC 也不会重新规划。

修复：`DefaultQueryExecMode = QueryExecModeExec`，并且 `SET plan_cache_mode=force_custom_plan`。作废的日志保留为 `bench-300k-INVALID-plancache.log`。

**这对生产也有影响**：如果在连接上 `SET hnsw.*` 或切换检索策略，而 pgx 缓存了计划，新设置可能不生效。建议用 `SET LOCAL` 放在事务里，同时用 `QueryExecModeExec` 或者对不同策略使用不同的 SQL 文本。

## 3. 结论

1. **正确性风险：planner 默认行为不能用。** 在过滤条件选择性很高时，planner 仍然会选 HNSW，但在默认 `iterative_scan=off` 下，1% 可见时平均只返回 **0.4 条**（要求 10 条），召回率 0.037。用户看到的就是"知识库里明明有，却检索不到"，而且没有任何报错。
2. **D-12 的预过滤方向成立，但需要分档执行**。可见比例或候选集大小不同，最优方案也不同：
   - 候选集小（可见 chunk 数 ≲ 1–3 万，相当于本次 1% 档）：**精确检索**，GIN 预过滤加排序，p95 < 3 ms，召回率 100%。这一档里 HNSW+iterative 反而又慢（26 ms）又不准（0.70）。
   - 候选集中等或大（10%–50%）：**HNSW + `hnsw.iterative_scan=relaxed_order` + `ef_search≥100`**，p95 2–4 ms，召回率约 0.96；ef=200 时约 0.99，耗时多 0.5 ms 左右。
   - 50% 可见时，GIN 精确检索要 300 ms，必须走 HNSW。
   - 实现方式：查询前用 `count` 或统计信息估算候选集大小（可以缓存每个 principal 集合的可见 chunk 数），再选策略，并用 `SET LOCAL` 设置参数。
3. **限定单个 KB 的检索**：在 KB 内走精确检索最好（0.4–14 ms，召回率 100%）。按 KB 分区能再提速 1.5–2 倍，但分区表的 HNSW 建索引慢了约 5 倍。**M0 建议先不分区**，单表加 `kb_id` 索引做精确检索已经足够；等单个 KB 超过约 10 万 chunk 时再评估。
4. 在单表上用 HNSW 检索单个 KB（`kb_id = $1` 过滤，KB 占全库 2%）效果很差：召回率 0.70–0.78，耗时 25–77 ms。**不要这样用。**
5. 物化可见文档或 semi-join 两种写法和 `acl &&` 写法差别不大。物化写法在 50% 档的精确检索反而更快，因为走了并行（116 ms 对 304 ms）。
6. relaxed_order 返回的结果可能略微乱序。本次 bench 的召回率按集合计算，不受影响；生产代码应在外层再按距离排序（pgvector 文档的建议）。**这一点本 spike 没有实现。**

## 4. 建议写入 PRD 的基线（需要在 100 万 × 1024 维上复测确认）

- 检索延迟（不含 embedding 和重排）：p95 ≤ 50 ms；本次 30 万数据上实测各档最优方案的 p95 都 ≤ 5 ms。
- 召回率（相对精确检索）：recall@10 ≥ 0.95。
- 验收测试必须包含"低可见比例（≤1%）下返回条数等于 k"这一用例，防止回退到 planner 默认行为。

## 5. 未测

- 100 万 × 1024 维规模、并发 QPS、写入时更新 HNSW 的开销、ACL 变更后的生效延迟、真实 embedding 分布、`max_scan_tuples` 调大的效果，均未测。
